# 架构

## 分层

| 层 | 目录 | 职责 |
| --- | --- | --- |
| 前端 | `crates/ui` | Vue 3 + Vite 前端源码；构建入口 `index.html`、`package.json`、`vite.config.ts`、`tsconfig.json`、`tsconfig.node.json`、`public/` 在仓库根，产物在根 `dist/` |
| 窗口壳 | `crates/app` | Tauri 2 窗口壳，包名与二进制名 `notecevia`；起应用并把前端命令接到内核 |
| 内核 | `crates/core` | 文档模型、块、撤销历史、对齐与分布；不碰文件与界面 |
| 存储 | `crates/store` | 工作区读写、媒体池、索引缓存、回收站、列表与搜索、容器与 HTML 导出和导入 |

依赖方向单向：`core` ← `store`、`core` ← `crates/app`、`store` ← `crates/app`；`crates/app` 只依赖 `tauri` 与 `tauri-plugin-opener`，还没加对 `core`、`store` 的路径依赖。

前端经 Tauri 命令调用窗口壳；窗口壳只注册示例命令 `greet`，尚未接上内核。

以下加载、保存与交互规则描述目标行为；其中自动保存、缩略图生成与索引刷新由界面层驱动，新界面尚未实现。

## 状态在哪

- 文档模型是 `core::Document`，撤销历史是 `core::History`：内存里的整份文档快照，栈最多 100 步；一次手势算一步。
- 脏标记由「当前文档与上次保存的快照」比较得出，撤销回到保存点时自动变干净。
- `store::Workspace` 里带一份索引缓存（`RefCell`），所以不是 `Sync`。

## 加载

- 打开工作区：不读索引；第一次列表、搜索或找最近画板时读 `index.cbor`。
- 索引缺失、写坏、格式号不符，或 boards/ 目录修改时间与画板文件数对不上：逐板重建一次，整份原子重写。打开时只做一次 readdir 与一次 metadata，不逐板 stat。
- `store` 提供强制重建索引的入口，外部程序改过工作区后不必重开。
- 停在首页时每 2 秒看一次 boards/ 目录的修改时间；外部新建、删除或改名画板会触发重建，列表自己刷新。原地覆盖写不改变目录时间，发现不了。
- 首页列表与搜索只读索引，不碰块文件；缩略图只在行真正绘制时按需读。
- 打开画板：读画板文件拿到目录，再按目录项读块文件；单个块坏了只丢那一段正文，位置保留。
- 媒体按内容哈希取原始字节，前端按需解码并缓存；取不到就画占位，不让整张画板打不开。

## 保存

自动保存的节拍与缩略图参数是目标值：新界面尚未实现，数值保留供实现时参照。

- 保存按块增量写：只写正文变过的块文件，其余块文件一个字节都不动；画板文件与索引仍然整份重写。所有写盘都是先写临时文件、落盘后改名。
- 写序先块后画板：中途失败最多留下没人引用的块，不会留下指向空处的目录项。
- 保存成功后，本画板不再被引用的块文件移进 `.trash/`；媒体不回收，可能还被别的画板引用。
- 索引整份原子重写：旧界面测量，一万张画板时单次保存约 39ms，其中包含索引编码与落盘。
- 自动保存：有改动时每 2 秒落一次盘；关窗时再存一次。压测 1000 块后 5 秒强杀进程，磁盘上 1000 个块文件与画板都在。
- 崩溃恢复：启动时清掉根目录与 boards/、blocks/、media/、thumbnails/ 一层的临时文件；更深的位置不扫。未保存的改动最多丢 2 秒。
- 缩略图在保存后生成，宽度 320 像素；自动保存很频繁，最多每 5 秒重画一次。
- 生成缩略图时把视图临时缩到内容全貌再取图，取完立刻还原；只在窗口不在前台时做，避免用户看到一帧缩放闪动。

## 交互优先级

- 打开画板是同步读盘：目录与块一次读完再画，还没有渐进加载与占位。画板规模变大时要先补这一层。
- 超过 100ms 的等待必须有可见反馈；保存、打开、导出都要有可见的结果反馈。
- 缩放是纯视图变换，不触发重排，不改变块的文档尺寸；绘制与交互都先按视口裁剪。
- 状态优先级：错误 > 未保存 > 普通状态；普通状态几秒后消失，错误常驻到下一次成功。
- 窗口用系统默认标题栏，没有自绘窗口按钮与系统命中区域。

## 性能预算

下列实测数字来自旧界面（egui），新界面尚未重测；预算本身不变。

| 指标 | 预算 | 实测（旧界面，一万张画板，release，本机） |
| --- | --- | --- |
| 启动到可交互 | ≤500ms | 首帧 514–534ms（一万张画板，见下） |
| 列表列出一万条 | ≤1.5s | 4ms |
| 一万条搜索 | ≤100ms | 13ms |
| 输入到屏幕可见 | ≤16ms | 帧时间 p50 16.7ms / p95 17.2ms（下界，见下） |
| 空闲内存 | ≤200MB | 应用 237MB；同机空 eframe 窗口 261MB |

- 首次打开没有索引的老工作区要先重建一次，一万张画板约 1.5 秒，之后才进上面的数字。
- 输入延迟只能量下界：旧界面的 egui 事件不带到达时间戳，量不到「输入→屏上出现」。用连续重绘下的帧时间作近似：空画布、1000 块画布与一万条首页都是 p50 16.7ms / p95 17.2ms，稳定在 60fps；真实输入延迟还要加上系统合成与显示延迟。
- 首页列表是虚拟滚动：只布局可见行，一万条下列表在连续重绘下仍是 60fps（虚拟化之前是每帧 90–100ms）。
- 绘制不慢：1000 块画板稳定 60fps，最大帧 46ms。保存也不卡：一千块画板只改一块时，全量写 1.77 秒，增量写 15ms；端到端自动保存的最大帧从 1474ms 降到 46ms。
- 冷启动分解（旧界面，一万张画板，release，本机）：打开工作区 467–488ms（其中窗口与图形栈初始化约占 470ms）、列表与索引校验 30–46ms、首帧合计 514–534ms。也就是 500ms 预算里约 470ms 是 eframe 的固定成本，应用自身的加载只占几十毫秒；与内存一样，这条预算的分母不是应用能控制的部分。
- 索引的一致性校验只在打开工作区后第一次用到时做一次；运行期间外部改文件，要重开工作区才能发现。
- 预算没覆盖的项按正确性优先，先交付再优化；超预算时按「列表 → 搜索 → 启动」的顺序查。
- 空闲内存的口径要重新定：旧界面在 release 下是 237MB（首页空/首页一张画板/画板视图分别是 237/237/239MB），而同一台机器上一个空的 eframe 窗口是 261MB。这 200MB 预算被图形栈的常驻开销本身占满，应用的状态与内容几乎不叠加。
- 下一步要么改成「扣除框架基线后的应用增量」这种可测的口径，要么换成堆分配统计；在那之前不要用这条预算判应用超支。
