# 架构

## 模块

| crate | 职责 |
| --- | --- |
| `core` | 文档模型、块、撤销历史、对齐与分布；不碰文件与界面 |
| `store` | 工作区读写、媒体池、索引缓存、回收站、列表与搜索、容器与 HTML 导出和导入 |
| `ui` | 画布渲染、物件操作、文本与表格编辑、画板首页、媒体纹理与缩略图、字体与主题 |
| `app` | 入口、装配、快捷键、自动保存、拖放、截图与导出落地 |

依赖方向单向：`core` ← `store`、`core` ← `ui`、`store` ← `app`、`ui` ← `app`。

## 状态在哪

- 文档只有一份，在 `ui::BoardApp` 里；`app` 只在保存时取只读引用。
- 撤销是内存里的整份文档快照，栈最多 100 步；一次手势算一步。
- 脏标记由"当前文档与上次保存的快照"比较得出，撤销回到保存点时自动变干净。
- 首页只产出动作（打开/新建/删除/重命名/标签/导出/搜索），读写由 `app` 执行。
- `store::Workspace` 里带一份索引缓存（`RefCell`），所以不是 `Sync`；目前只在 UI 线程用。

## 加载

- 打开工作区：不读索引；第一次列表、搜索或找最近画板时读 `index.cbor`。
- 索引缺失、写坏、格式号不符，或画板编号集合与「文件长度 + 修改时间」对不上：逐板重建一次，整份原子重写。
- 首页的「刷新」按钮（Ctrl+R）会强制重建索引，外部程序改过工作区后不用重开。
- 停在首页时每 2 秒看一次 boards/ 目录的修改时间；外部新建、删除或改名画板会触发重建，列表自己刷新。原地覆盖写不改变目录时间，发现不了。
- 首页列表与搜索只读索引，不碰块文件；缩略图只在行真正绘制时按需读。
- 打开画板：读画板文件拿到目录，再按目录项读块文件；单个块坏了只丢那一段正文，位置保留。
- 媒体按内容哈希取原始字节，界面按需解码成纹理并缓存；取不到就画占位，不让整张画板打不开。

## 保存

- 每次保存重写这张画板的画板文件与全部块文件，先写临时文件、落盘后改名。
- 写序先块后画板：中途失败最多留下没人引用的块，不会留下指向空处的目录项。
- 保存成功后，本画板不再被引用的块文件移进 `.trash/`；媒体不回收，可能还被别的画板引用。
- 索引整份原子重写：一万张画板时单次约 42ms，其中包含索引编码与落盘。
- 自动保存：有改动时每 2 秒落一次盘；关窗时再存一次。压测 1000 块后 5 秒强杀进程，磁盘上 1000 个块文件与画板都在。
- 崩溃恢复：启动时清掉没写完的临时文件，未保存的改动最多丢 2 秒。
- 缩略图在保存后从当前画面生成，宽度 320 像素；自动保存很频繁，最多每 5 秒重画一次。

## 交互优先级

- 首屏优先：先出结构与占位，再出内容。
- 超过 100ms 的等待必须有可见反馈，空白是最差的反馈。
- 缩放是纯视图变换，不触发重排，不改变块的文档尺寸。
- 状态优先级：错误 > 未保存 > 普通状态；普通状态几秒后消失，错误常驻到下一次成功。

## 性能预算

| 指标 | 预算 | 实测（一万张画板，release，本机） |
| --- | --- | --- |
| 启动到可交互 | ≤500ms | 启动读最近画板 324ms |
| 列表列出一万条 | ≤1.5s | 2.8ms |
| 一万条搜索 | ≤100ms | 16ms |
| 输入到屏幕可见 | ≤16ms | 未实测 |
| 空闲内存 | ≤200MB | 应用 237MB；同机空 eframe 窗口 261MB |

- 首次打开没有索引的老工作区要先重建一次，一万张画板约 1.85 秒，之后才进上面的数字。
- 索引的一致性校验只在打开工作区后第一次用到时做一次；运行期间外部改文件，要重开工作区才能发现。
- 预算没覆盖的项按正确性优先，先交付再优化；超预算时按「列表 → 搜索 → 启动」的顺序查。
- 空闲内存的口径要重新定：应用在 release 下是 237MB（首页空/首页一张画板/画板视图分别是 237/237/239MB），而同一台机器上一个空的 eframe 窗口是 261MB。也就是说这 200MB 预算目前被图形栈的常驻开销本身占满，应用的状态与内容几乎不叠加。
- 下一步要么改成「扣除框架基线后的应用增量」这种可测的口径，要么换成堆分配统计；在那之前不要用这条预算判应用超支。
