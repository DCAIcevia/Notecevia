# 开工与预算

## 为什么要有预算

上下文是有限资源。读错文件不只是浪费时间，还会用无关信息稀释判断——读得越多，越容易把边角细节当成重点。把探索从默认行为改成需要理由的行为，是这个项目最重要的协作约定。

一次任务最多读 5 个文件、检索 3 次、列目录 1 次、单次读 200 行。超了就先停下来说清楚：已经确认什么、还缺什么，然后提一个问题，或者给一个可逆的假设继续。

## 怎么找文件

先用符号名或报错串检索拿到候选文件，再只读命中点上下 50 行。需要调用关系时读签名不读实现；需要第三方 API 时查 docs.rs，不凭记忆写签名——记忆里的签名经常差一个参数或一个版本。

会话开始时只读根 `AGENTS.md` 和任务点名的文件。`target/`、生成物、日志、全量 `git log`、递归列目录，这些读完对判断没有帮助；"先把仓库熟悉一遍"是最常见的浪费。

## 什么时候必须问

产品行为、数据格式、对外接口、依赖选择、功能范围、视觉方向——这几类做错，要么回滚用户数据，要么重写两个以上模块。遇到它们先停手，问一个问题，而不是挑一个看起来合理的方案继续做。

命名、局部实现、样式细节这类做错了一行就能改回来的事，直接做，汇报时提一句。中间地带（默认排序、快捷键、默认文件名）写进声明的「假设」里。

## 什么情况下停

同一问题验证两次还失败、遇到上面那类决策、发现规则自相矛盾、预算用完又想不出可逆方案——停下来，报告已知事实和可选项，等人决定。继续试错只会把错误做大。

## 怎么汇报

四段：改动（文件 → 一句话）、验证（命令与结果）、风险（没覆盖的边界）、后续（需要人裁决的事）。不写"已完成"却不给证据。
