# 代码

## 分层是为了能换掉 UI

`core` 放领域逻辑与用例，不碰文件、时钟、随机数、界面类型；`store` 做读写与索引；`ui` 只把状态映射成界面；`app` 负责组装。依赖只能单向。

这样分的原因很实际：GUI 框架是整套技术栈里最容易被换掉的一层，把它挡在 `ui` 里，换的时候不用碰领域逻辑；领域逻辑不碰 IO，就能用临时目录和假时钟直接测。

## 错误要能被区分

库内用 `thiserror` 定义错误变体，让调用方判断是哪一类失败；应用边界用 `anyhow` 加上下文（`.context("保存笔记失败")`）。运行时路径不要 `unwrap()`——崩溃信息对用户没意义，对排查也没有纵深。`panic!` 只留给违反不变式的情况，并在注释里写清不变式是什么。

## 命名与规模

领域词表固定：Note 笔记、Tag 标签、Workspace 工作区、Trash 回收站。代码与界面用词一致，用户看到的和代码里读到的才对得上。布尔量用 `is_`／`has_`。

模块按领域切，不出现 `utils`、`helpers`、`common`——这类目录会慢慢吸收一切。单文件 ≤400 行、单函数 ≤50 行是提醒，不是铁律；超了先想是不是职责混了。

## 测试放在会被破坏的地方

`core` 的公开函数至少一个用例；`store` 用临时目录做集成测试，覆盖原子写、路径逃逸、未知字段保留、回收站恢复——这四件事坏了的代价是丢用户数据。每个缺陷修复带一个能复现它的测试。

测试不依赖网络、系统时间、真实用户目录，否则会在 CI 上随机失败。

## 门禁与性能

提交前三条命令全绿：`cargo fmt --all --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace`。

性能预算是给未来的自己看的：冷启动 ≤500ms、1 万条列表 ≤1.5s、1 万条搜索 ≤100ms、输入延迟 ≤16ms、空闲内存 ≤200MB。超了先说明原因，不要默默接受。

## 依赖

标准库能合理实现就不加依赖。加之前确认维护活跃、许可证兼容（MIT／Apache-2.0），说清用途、替代方案与体积风险。直接依赖超过 40 个时停下来讨论——每个依赖都要跟着升级，不是免费的。
