# Rust 代码

## 分层

- `core`：领域逻辑，禁止文件 IO、时钟、随机数、UI 类型；副作用通过 trait 注入。
- `store`：实现 IO 与索引，依赖 `core`。
- `ui`：只做状态到视图的映射、事件转发；依赖 `core`，不依赖 `store`。
- `app`：组装，依赖 `store` 与 `ui`。
- 越界依赖视为违规。

## 错误

- 库内错误用 `thiserror`，变体可被调用方区分。
- 应用边界用 `anyhow` 并附 `.context("……失败")`。
- 运行时禁止 `unwrap()`／`expect()`；测试可 `expect("原因")`。
- `panic!` 只用于违反不变式，注释写明不变式。
- 用户可见错误转成「发生了什么 + 怎么办」；技术细节只进日志。

## 命名

- 遵循 Rust 惯例，不自创缩写。
- 词表固定：Note 笔记、Tag 标签、Workspace 工作区、Trash 回收站。
- 布尔量 `is_`／`has_`，命令用动词。

## 规模

- 单文件 ≤400 行，单函数 ≤50 行；超了在汇报里说明理由。
- 模块按领域切分，禁止 `utils`、`helpers`、`common`。
- 公共 API 有文档注释，一句话说清用途与副作用。
- `#[allow(...)]` 必须附理由注释。

## 测试

- `core` 每个公开函数至少一个用例。
- `store` 用临时目录做集成测试：原子写、路径逃逸拦截、未知字段保留、回收站恢复。
- 每个缺陷修复带一个能复现它的测试。
- 测试不依赖网络、系统时间、真实用户目录。

## 门禁

`cargo fmt --all --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace`，三条全绿才算完成。

## 性能预算

冷启动 ≤500ms、1 万条列表 ≤1.5s、1 万条搜索 ≤100ms、输入延迟 ≤16ms、空闲内存 ≤200MB。超出先说明，不默默接受。

## 依赖

- 标准库能合理实现就不加。
- 近 12 个月有维护，或属于事实标准。
- 许可证 MIT／Apache-2.0 兼容。
- 先说清用途、替代方案、体积与维护风险，再动手。
- 直接依赖超过 40 个必须停下来讨论。

## 日志

用 `tracing`：`error` 用户可感知失败，`warn` 降级运行，`info` 生命周期，`debug` 细节。日志不含笔记正文。`println!`／`dbg!` 不进提交。
