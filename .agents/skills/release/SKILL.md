# Release

This skill owns the decisions a release makes: where the version lives, what must be true before a tag is pushed, and what a published release must contain. The mechanics are repository text — [CONTRIBUTING.md](../../../CONTRIBUTING.md) owns the version-source sentence and the four prep steps, and [.github/workflows/release.yml](../../../.github/workflows/release.yml) is the executable definition of every job, condition, and asset. Both are linked, not copied; the workflow file wins on any disagreement.

## One version, one immutable tag

- `[workspace.package] version` in Cargo.toml is the only version. `package.json` repeats it so the frontend build agrees, and `Verify release` fails when the two differ.
- `crates/app/tauri.conf.json` must not carry a `version` key; the installer version comes from Cargo, and the same job throws when the key appears. A pinned copy is a second source that drifts from the tag.
- `Cargo.lock` records the workspace versions as well. A bump that skips it leaves a lock file the `--locked` CI build rejects; `pnpm release:bump` updates it in the same run.
- `v*` tags are ruleset-protected: not deletable, not movable. A tag pushed at the wrong version cannot be repaired, only abandoned and re-released under a new version.

## Before the tag

[CONTRIBUTING.md](../../../CONTRIBUTING.md) defines the four steps. Each one exists because skipping it fails later, after the tag can no longer be fixed:

1. Run `pnpm release:bump <version>`. One command rewrites the workspace version in `Cargo.toml`, the copy in `package.json` and the matching `Cargo.lock` entries, then creates a changelog template. It rejects a non-semver, a missing workspace version, or a `version` key in `tauri.conf.json` before writing anything, and re-reads both files afterwards to prove they agree. It does not choose the number: whether an alpha continues or becomes the next release is a product decision.
2. Fill in the `changelog/<version>.md` the bump created, one file per public release, grouped as the [changelog index](../../../changelog/README.md) describes.
3. Run the three gates from [AGENTS.md](../../../AGENTS.md). Verify runs the same three with `--locked`, so a green local run is the only way to know the tag will not go red.
4. Trigger `Release` by `workflow_dispatch` with the candidate version. The dry run performs verify plus the three platform builds and skips `Publish release`; it is the only rehearsal available while the tag is still unsent.

## What a tag publishes

The workflow runs three stages in order:

1. `Verify release` — tag commit reachable from `main`, version agreement, third-party license drift, the gates.
2. `Build (linux | windows | macos)` — one installer set per platform.
3. `Publish release` — license copies, SPDX SBOM, `SHA256SUMS`, build provenance and SBOM attestations, then draft to published.

- Assets: Windows NSIS always and MSI for a stable version; Linux deb and AppImage; macOS dmg; plus `LICENSE`, `NOTICE`, `THIRD_PARTY_LICENSES.md`, one `SHA256SUMS` covering every other asset, and one SBOM.
- The release is immutable. Assets upload to a draft and the draft is published in the same run, so a missing asset cannot be added afterwards — it needs a new version.
- A tag containing `-` publishes as a prerelease. MSI version segments take digits only, which is why a prerelease ships NSIS alone on Windows while Linux and macOS keep their full set.

## Licenses

- `THIRD_PARTY_LICENSES.md` is generated by cargo-about from the locked dependency graph and shipped beside the binaries. The generation command is in [CONTRIBUTING.md](../../../CONTRIBUTING.md); any dependency change makes the file stale, and stale fails verify.
- `about.toml`'s `accepted` list must equal `deny.toml`'s `allow` list. One generates, the other audits: a license accepted by only one passes locally and fails in CI, or the reverse.
- Generation is pinned to `x86_64-pc-windows-msvc` so a different host cannot add platform-only dependencies, and workspace crates are excluded as private.
- A new third-party license is a dependency decision, not a release detail: adding it to both lists follows a user's decision on the dependency, which [AGENTS.md](../../../AGENTS.md) reserves for them.

## Boundaries

- Never delete or move a published tag, and never re-point one to a different commit. Deleting a protected tag is refused anyway; asking for it means the version discussion is the real task.
- A failed release is not retried by tagging the same version again. The tag is immutable, so fix forward under a new version, or stop and ask.
- Publishing is not "push a tag and see". The dry run exists so the tag push is the last step of a release, never the first.
- Version numbers and whether to release at all are human decisions. Ask before choosing a version, cutting a release, or abandoning one.
- The bump commit itself: [git-commit skill](../git-commit/SKILL.md). Reviewing the release diff: [code-review skill](../code-review/SKILL.md). Changelog prose: [docs.md](../project-rules/references/docs.md).

## Verification

- Dry run: dispatch `Release` with the candidate version. The run is named `Release dry run <version>`, `Verify release` and all three `Build` jobs go green, and `Publish release` is absent — its absence is the proof the run rehearsed rather than shipped.
- Published release: every asset in the matrix is listed, `SHA256SUMS` covers all of them, the SBOM and attestations exist, the release is not a draft, and the prerelease flag matches the `-` in the tag.
- Negative cases that must turn the run red: a tag whose name disagrees with `Cargo.toml`, a version bumped in one file only, a `version` key added to `tauri.conf.json`, a stale `THIRD_PARTY_LICENSES.md`. A green verify with any of those present would let a mislabeled or mislicensed artifact reach users, which is the failure this whole gate exists to prevent.
